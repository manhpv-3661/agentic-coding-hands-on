## 2. Single gutter / max-width verdict

- **PageGutter = 144px** at the native 1512px frame (confirmed 3×: header `12px 144px`, `Bìa` `96px 144px`, and by extension every section nested inside `Bìa`). This is a single, consistent value across every section checked — matches current `app/components/layout/page-layout.tsx` `GUTTER_CLASS` `lg:px-36` (144px). **No gutter mismatch.**
- **ContentWidth is not a single value — it's the two-tier system the code already encodes**: `1224px` (hero / awards outer / sun-kudos outer — i.e. `Bìa`'s "primary column", `1512 − 2×144`) and a narrower `1152px` for root-further's own card, plus a `1120px` inner card for sun-kudos's visual promo box. All three widths (`1120/1152/1224`) are the exact ones already defined in `CONTENT_WIDTH_CLASS` in `page-layout.tsx` — the primitive's shape matches the design's shape, not a guess.
- Root-further's 1152 centers to x=180 (not x=144) because it's narrower than the shared 1224 column — `PageGutter(144) + ContentFrame(1152)` reproduces exactly this (144 + (1224−1152)/2 = 180). Verified numerically equal to the Figma `startX`. **Not a bug** — nesting math already matches.
- Sun-kudos nests `ContentFrame(1224)` → `ContentFrame(1120)`. This is **not** a rule-3 violation ("no nested horizontal padding") because neither `ContentFrame` adds padding — only `max-w` + `mx-auto` centering — and the two-level nesting reproduces the actual two-level Figma structure (`mms_D1_Sunkudos` 1224 region containing a narrower 1120 visual card), confirmed by the 196px absolute offset matching 144+(1224-1120)/2 exactly. **Correctly modeled, not double-padding.**
- `app/page.tsx`'s `<main className="... lg:gap-[120px] lg:py-24">` (py-24=96px, gap-120px) exactly reproduces `Bìa`'s measured `padding:96px .. 96px` / `gap:120px`. **Matches.**

## 3. Mismatch classification (rule 5 of the layout system doc)

Went through hero, awards, sun-kudos, root-further, site-header against live numbers. **No numeric mismatch found** in gutter, max-width, section padding/gap, or the typography sampled (award heading 57/64/-0.25/700, award caption 24/32/700, root-further body 24/32/700 + pull-quote 20/32/700, sun-kudos eyebrow/title/body) — all match `app/components/home/*.tsx` current values exactly. This is consistent with the repo's recent history (`ce016b0 fix: further MoMorph pixel-conformance corrections`, `266c38e`, `a6414a3`) already having driven these numbers to ground truth before this audit.

One thing worth flagging as a **documentation/measurement-method risk**, not a code bug:
- **Wrong-source-of-truth trap (classification: "wrong spacing token" if ever "fixed" naively):** the award grid's raw MoMorph `styles.gap` reports `"80px"` for the row (`2167:9074`/`2167:9078`), but the row uses `justifyContent: space-between`, so the *effective* rendered horizontal gap is `108px` (computed from `1224 − 3×336 = 216`, `/2 = 108`). The current code (`awards-section.tsx`, `lg:gap-x-[108px]`) already uses the correct **effective** value, not the raw style string. If anyone re-derives this from the raw `get_node` JSON without cross-checking position deltas, they'd "fix" a working 108px into a wrong 80px. Documenting this so `momorph-layout-system.md` §7 ("verification is numeric") gets applied to *effective* gap, not the raw auto-layout `gap` field, whenever `justify-content` is anything other than `flex-start`.
